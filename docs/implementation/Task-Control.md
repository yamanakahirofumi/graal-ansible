# タスク制御の実装詳細 (Task Control Implementation)

本ドキュメントでは、`graal-ansible` におけるタスクの実行制御（条件分岐、ループ、変数登録、ハンドラー、ブロック、リトライ等）の実装方法について詳述します。

## 1. 条件分岐 (`when`)

タスクの実行を特定の条件に基づいて制御します。

- **実装方針**:
    - `when` 句に記述された Jinja2 式を `VariableResolver` (Jinjava) を用いて評価します。
    - 評価結果が `true` または真とみなされる値（非空の文字列、非ゼロの数値等）の場合のみ、タスクを実行します。
    - 評価結果が `false` の場合、そのホストでのタスク実行はスキップされ、結果には `skipped=true` が含まれます。
    - `when` 句がリスト形式で記述されている場合は、すべての条件が `true` であること（論理積）を確認します。
- **留意点**:
    - Jinja2 の式として評価するため、変数は `{{ }}` で囲まずに記述されることが一般的であることに対応します。
- **データ構造**:
    - `Task` レコードに `Object when` フィールド（String または List<String>）を保持します。

## 2. ループ (`loop`)

同一のタスクを複数のアイテムに対して繰り返し実行します。

- **実装方針**:
    - `loop` フィールドに指定されたリスト（またはリストを返すテンプレート）を解析します。
    - リストの各アイテムについて、特殊変数 `item` にその値を割り当て、タスクを繰り返し実行します。
    - 各イテレーションの結果は、最終的なタスク結果の `results` リストに格納されます。
- **レガシー対応**:
    - `with_items`, `with_dict`, `with_list` 等のレガシーなループ構文は、内部的に `loop` 処理へ変換されます。
    - **with_items**: 渡されたリストを1段階平坦化（flatten）してからループします。内部的には `loop: "{{ list | flatten(levels=1) }}"` 相当の処理が行われます。
    - **with_dict**: 辞書を `key`/`value` のペアを持つリストに変換してループします。内部的には `loop: "{{ dict | dict2items }}"` 相当の処理が行われます。
    - **with_list**: 渡されたリストを平坦化せずにそのまま `loop` へ渡します。
- **データ構造**:
    - `Task` レコードに `Object loop` フィールドを保持します。

### 2.1 ループ制御 (`loop_control`)

`loop` の振る舞いを詳細に制御します。

- **実装方針**:
    - **index_var**: 現在のループインデックス（0開始）を格納する変数名を指定します。
    - **loop_var**: 各イテレーションのアイテムを格納する変数名を指定します（デフォルトは `item`）。
    - **label**: 実行結果の出力に使用するテンプレートを指定します。複雑な辞書をループする場合に、特定のキーのみを表示してログを整理するのに役立ちます。
    - **pause**: 各アイテムの実行間に挿入する待ち時間（秒）を指定します。
- **データ構造**:
    - `Task` レコードに `Map<String, Object> loop_control` フィールドを保持し、`YamlParser` で解析可能とします。
- **実行エンジンへの統合**:
    - `TaskExecutor.executeLoopTask` において、`index_var` のカウントアップ、`loop_var` による変数名の動的な切り替え、および `pause` による待機処理を実装します。

## 3. 変数登録 (`register`)

タスクの実行結果を後のタスクで利用するために変数として保存します。

- **実装方針**:
    - タスク実行後、`register` キーで指定された名前で、実行結果（`TaskResult` のデータ部分）を `VariableManager` に登録します。
    - 登録された変数は、同一 Play 内の以降のタスクで参照可能です。
- **データ構造**:
    - `Task` レコードに `String register` フィールドを保持します。
    - 登録される変数は Map 形式とし、Ansible 互換のフィールド名（`rc`, `stdout`, `stderr`, `changed`, `failed` 等）を保持します。

## 4. ハンドラーと通知 (`handlers`, `notify`)

タスクによって状態が変更された（`changed=true`）場合にのみ実行される特別なタスクを制御します。

- **実装方針**:
    - **通知 (Notify)**: タスクが実行され、結果が `changed=true` かつ `notify` 句がある場合、指定されたハンドラー名またはトピックを「実行待ちキュー」に登録します。
    - **トピックの購読 (Listen)**: ハンドラーは `listen` キーワードを使用して、特定のトピックを購読できます。通知された名前がハンドラー名と一致するか、`listen` に指定されたトピックと一致する場合に、そのハンドラーが実行対象となります。
    - **実行タイミング**: プレイ（Play）内のすべての通常タスクが完了した直後、または `flush_handlers` タスクが実行されたタイミングで、キューに溜まったハンドラーを順次実行します。
    - **冪等性・重複排除**: 同一のハンドラー（`Task` オブジェクト）は、一つのハンドラーフラッシュサイクル内において、複数の通知（名前またはトピック）によってトリガーされたとしても、一度だけ実行されます。
- **データ構造**:
    - `Task` レコードに `List<String> notifications` (YAMLでは `notify`) および `List<String> listen` フィールドを保持します。
    - `Play` レコードに `List<Task> handlers` フィールドを保持します。

## 5. ブロック (`block`, `rescue`, `always`)

複数のタスクを論理的にグループ化し、エラーハンドリング（例外処理）を行います。

- **実装方針**:
    - **block**: グループ化された一連のタスクを順次実行します。
    - **rescue**: `block` 内のタスクでエラー（failed）が発生した場合にのみ実行されるタスク群です。
    - **always**: `block` の成否に関わらず、最後に必ず実行されるタスク群です。
- **留意点**:
    - ブロック自体も `when` 句による条件分岐が可能です。
- **データ構造**:
    - `Task` またはそれに準ずる `Block` レコードとして定義し、タスクのリストを保持します。

## 6. 結果のカスタマイズ (`failed_when`, `changed_when`)

モジュールの標準的な成功/変更判定を上書きします。

- **実装方針**:
    - **failed_when**: 指定された条件式が `true` の場合、モジュールが成功していても `failed=true` とみなします。リストで指定された場合は、すべての条件が `true` の場合に失敗とみなされます（暗黙の AND）。
    - **changed_when**: 指定された条件式が `true` の場合、モジュールに変更がなくても `changed=true` とみなします。逆に `false` を指定して常に変更なしにすることも可能です。リストで指定された場合は、すべての条件が `true` の場合に変更とみなされます（暗黙の AND）。
- **実行タイミング**: モジュール実行完了直後、`register` や `notify` の処理前に行います。

## 7. リトライ処理 (`until`, `retries`, `delay`)

タスクが特定の条件を満たすまで、繰り返し実行します。

- **実装方針**:
    - **until**: 条件式が `true` になるまで繰り返します。
    - **retries**: 最大試行回数（デフォルト 3）。
    - **delay**: 試行間の待ち時間（秒、デフォルト 5）。
- **評価順序**:
    1.  モジュールを実行。
    2.  `failed_when` および `changed_when` を評価し、そのイテレーションの結果を確定。
    3.  `until` 条件を評価。
    - 各イテレーションにおいて、`until` 条件のチェック前に結果のカスタマイズが適用される点に留意してください。
- **留意点**:
    - 各試行の結果は `register` された変数（`results` リスト）に蓄積される必要があります。

## 8. 委譲と実行制御 (`delegate_to`, `run_once`, `ignore_errors`, `ignore_unreachable`, `delegate_facts`)

これらのキーワードは `Task` レコードおよび `YamlParser` に定義されており、パース可能です。ただし、実行エンジンにおける詳細な振る舞いの実装状況は以下の通りです。

- **delegate_to**:
    - **ステータス**: `TaskExecutor.executeSingleTask` にて、変数解決（Jinja2 展開）およびコネクションの動的な切り替えを実装済み。
    - **実装詳細**: `VariableManager.getVariablesForHost(String, Play)` を使用して、委譲先ホストの変数を現在のプレイコンテキスト（プレイレベルの変数や `vars_files` を含む）で高精度に解決します。
- **run_once**:
    - **ステータス**: `TaskQueueManager.executePlay` にて、1つのホストで実行されたら以降のホストをスキップする基本ロジックが実装済み。
- **ignore_errors**:
    - **ステータス**: `TaskQueueManager.executeTaskOnHost` にて、失敗しても `failedHosts` に追加しないロジックが実装済み。
- **ignore_unreachable**:
    - **ステータス**: `TaskQueueManager.executePlay` および `executeTaskOnHost` にて実装済み。
    - **実装内容**: コネクション確立時やコマンド実行時に接続不可（Unreachable）エラーが発生した場合、通常は該当ホストをプレイから除外しますが、このフラグが `true` の場合はエラーを無視して継続します。
- **delegate_facts**:
    - **ステータス**: `TaskQueueManager.executeTaskOnHost` にて実装済み。
    - **実装内容**: `delegate_to` と併用された際、収集されたファクト（`ansible_facts`）の保存先を制御します。`true` の場合、モジュール実行結果に含まれるファクトを、委譲先ホストではなく元のホスト（`inventory_hostname`）に紐付けて登録します。

## 9. 環境変数 (`environment`)

タスク実行時の環境変数を定義します。

- **実装方針**:
    - **マージルール**: `environment` は Play, Block, Task の各レベルで定義可能です。
        - 優先順位は **Task > Block > Play** です。
        - 同一キーの環境変数が複数のレベルで定義されている場合、より低い（Taskに近い）レベルの値が優先されます。
        - 異なるキーの変数はマージされ、最終的な環境変数セットとして構築されます。
    - **テンプレート評価**:
        - `environment` フィールド（Map または Map を返す文字列）は、タスク実行の直前に `VariableResolver` を用いて遅延評価（Lazy Evaluation）されます。
        - これにより、`register` 変数や `loop` の `item` を環境変数内で動的に参照可能です。
    - **伝播**:
        - 評価結果の Map は、`TaskExecutor` を経由してコネクションプラグインの `execCommand` メソッドに渡されます。
        - コネクションプラグインは、この Map を実際のプロセス実行環境（`ProcessBuilder` の `environment()` や SSH の環境変数設定）に反映します。
- **データ構造**:
    - `Play`, `Task` レコードに `Object environment` フィールドを保持します。
    - 評価後のデータ型は `Map<String, String>` となります。

## 10. インタラクティブ・プロンプト (`vars_prompt`)

プレイの開始時にユーザーに入力を求める仕組みです。

- **実装方針**:
    - `Play` レコードに `vars_prompt` の定義を保持します。
    - プレイ実行の直前に、定義された変数ごとにユーザーへの入力を試みます。
    - **PromptProvider**: インタラクティブな入力を抽象化するため、`PromptProvider` インターフェースを導入します。
        - デフォルトの実装（`ConsolePromptProvider`）は標準入力から読み取ります。
        - テストや自動実行環境では、事前定義された回答を返すモック実装を使用可能です。
    - **スキップ条件**:
        - 対象の変数が既に `extra_vars` (Level 22) など、より高い優先度で定義されている場合は、プロンプトを表示せずにスキップします。
    - **変数優先順位**: 収集された値は Level 13 (Play `vars_prompt`) として登録されます。

## 11. チェックモード (`check_mode`)

タスクをチェックモード（ドライラン）で実行するかどうかを制御します。

- **実装方針**:
    - `check_mode` フィールドに指定された値（`yes`/`true`, `no`/`false`）を評価します。
    - コマンドライン引数で `-C` / `--check` が指定されている場合、全てのタスクはデフォルトでチェックモードとなりますが、`check_mode: no` が指定されているタスクは強制的に通常実行されます。
    - チェックモードで実行されるモジュールは、システムに変更を加えずに、変更が発生するかどうかのみを報告します。
- **データ構造**:
    - `Task` レコードおよび `Play` レコードに `Object check_mode` フィールドを保持します。

## 12. 実行エンジンにおける処理の分離と順序

本プロジェクトでは、`PlaybookExecutor` (PE)、`TaskQueueManager` (TQM)、`TaskExecutor` (Worker) の3層構造でタスクを制御します。各コンポーネントの責務と実行順序は以下の通りです。

### 12.1 コンポーネント間の責務分離

- **PlaybookExecutor (PE)**: Playbook 全体の進行管理。
- **TaskQueueManager (TQM)**:
    - ターゲットホストのループ。
    - `block/rescue/always` のオーケストレーション。
    - ブロックレベルの `when` 条件の評価。
    - ハンドラーの実行管理 (`flush_handlers`)。
- **TaskExecutor (Worker)**:
    - タスクレベルの変数解決（Jinja2 展開）。
    - タスクレベルの `loop` の展開とイテレーション。
    - タスクレベル（およびイテレーションごと）の `when` 条件の評価。
    - `until/retries` によるリトライ制御。
    - モジュール/Action Plugin の実行。
    - `failed_when/changed_when` による結果のカスタマイズ。

### 12.2 タスク実行のライフサイクル

1.  **ホストの選択 (TQM)**: Play で定義されたターゲットホストを特定し、`limit` オプションによるフィルタリングを適用します。
2.  **ブロック制御 (TQM)**: タスクが `block` の場合、ブロックレベルの `when` を評価し、子タスクを実行します。
3.  **変数の集約 (Worker)**: Play, Host, Task 各レベルの変数を集約します。
4.  **ループの展開 (Worker)**: `loop` がある場合、リストを取得しイテレーションを開始します。
5.  **条件評価 (Worker)**: `when` 句を評価し、実行の可否を判断します。
6.  **委譲の判定 (Worker)**: `delegate_to` がある場合、接続先を解決します。
7.  **環境変数とチェックモードの解決 (Worker)**: `environment` および `check_mode` を最終決定します。
8.  **実行とリトライ (Worker)**:
    - `until` がある場合、条件を満たすか最大回数に達するまで繰り返します。
    - 実際のモジュール実行を行います。
9.  **結果の補正 (Worker)**: `failed_when`, `changed_when` を評価し、成功/変更ステータスを確定させます。
10. **結果の登録と通知 (TQM)**:
    - `register` がある場合、結果を変数に保存します。
    - `changed=true` の場合、`notify` に基づきハンドラーをマークします。
11. **エラーハンドリング (TQM)**: 失敗時に `ignore_errors` が `false` ならば、そのホストを失敗としてマークし、必要に応じて `rescue` ブロックを実行します。

## 13. 包含とインポート (Include and Import)

外部ファイルで定義されたタスクやプレイブック、ロールを現在の実行コンテキストに取り込む仕組みです。

### 13.1 タスクの包含 (`include_tasks`, `import_tasks`)

外部ファイルで定義されたタスクリストを現在の Play に取り込みます。

- **実装方針**:
    - `include_tasks` または `import_tasks` キーに指定されたファイルパス（テンプレート可）を解決します。
    - ファイル内のタスクリストを読み込み、現在の実行コンテキスト（変数、タグ等）を継承させつつ実行します。
- **ホストパターンの解決**:
    - 取り込まれるタスクが特定のホストやグループを対象とする場合、`TaskQueueManager` はインベントリ全体の階層構造を再帰的に検索（`getAllHosts`）して、一致する全てのホストを正確に特定します。これにより、深い階層にあるグループに対しても漏れなくタスクが適用されます。
- **パラメータの伝播**:
    - `include_tasks` 時に渡された引数（Level 21 変数）は、取り込まれた子タスクに明示的に継承され、変数優先順位に従って解決されます。

### 13.2 プレイブックのインポート (`import_playbook`)

トップレベルのディレクティブとして、他のプレイブックファイルをインポートします。

- **実装方針**:
    - `YamlParser` において、通常の `plays` リストの解析と並行して `import_playbook` ステートメントを処理します。
    - インポートは再帰的にサポートされており、インポートされたプレイブック内の `import_playbook` も正しく展開されます。
- **変数の伝播とマージ**:
    - インポート時に指定された変数やタグは、インポート先のプレイブックに含まれるすべてのプレイおよびタスクに伝播されます。
    - 実行エンジンは、インポート階層を辿りながらこれらのコンテキストを正しくマージして保持します。

### 13.3 ロールの包含・インポート (`include_role`, `import_role`)

定義済みのロールを動的（include）または静的（import）にタスクとして実行します。

- **実装方針**:
    - `TaskQueueManager` において Java によるエミュレーション実装を行っています。
    - ロール名に基づき、標準的なディレクトリ構造（`roles/<role_name>/`）を検索し、`tasks/main.yml`（または `tasks_from` で指定されたファイル）を読み込みます。
- **変数優先順位 (Level 15 および Level 20)**:
    - ロール内の `vars/main.yml` で定義された変数は、**Level 15 (Role variables)** として登録されます。
    - ロール呼び出し時に渡されたパラメータ（例: `vars:` 句）は、**Level 20 (Role parameters)** として登録されます。
    - これにより、プレイ変数（Level 12）などを適切に上書きしつつ、`extra_vars`（Level 22）による上書きを許容する Ansible 互換の優先順位を実現しています。
- **コンテキストの分離**:
    - ロール実行中は、そのロール固有の変数が優先的に解決されるよう、`activeRoles` コンテキストをスタック状に管理して実行エンジンに伝播させます。

## 14. タグ (`tags`) と 実行制限 (`limit`)

Playbook の実行対象を動的に制御する仕組みの実装について。

### 14.1 タグの継承と解決
- **継承ロジック**:
    - `YamlParser` において、`Play` レベルで定義された `tags` はその Play 内のすべての `Task` オブジェクトの `tags` リストにマージされます。
    - 同様に、`block` 内のタスクは、`block` 自身に定義された `tags` を継承します。
- **解決順序**: マージされた後の `tags` リストに基づいて、`TaskQueueManager` または `TaskExecutor` が実行の可否を判断します。

### 14.2 タグの評価アルゴリズム
- **基本ルール**:
    - `--tags` が指定されている場合: タスクのタグリストが、指定されたタグのいずれかを含んでいる、または `always` タグを含んでいる場合に実行します。
    - `--skip-tags` が指定されている場合: タスクのタグリストが、指定されたタグのいずれかを含んでいる場合にスキップします。ただし、`always` タグは `--skip-tags always` が明示されない限り実行されます。
- **特殊タグの処理**:
    - `always`: 指定されたタグに関わらず実行されます。
    - `never`: 明示的に指定されない限り実行されません。

### 14.3 実行制限 (`limit`) の実装
- **ホストの解決**: `TaskQueueManager.getTargetHosts` メソッドにて、Play の `hosts` パターンによって抽出されたホストリストに対し、`limit` パターンを適用して最終的なターゲットを決定します。
- **パターンのサポート**:
    - 単一のホスト名またはグループ名。
    - カンマ区切りのリスト (`host1,host2,group1`)。

## 15. 真偽判定 (Truthiness)

Jinja2 テンプレートや `when` 句、`failed_when` 等の評価において、Ansible 互換の真偽判定（Truthiness）を採用しています。

- **実装方針**: `org.example.ansible.util.Truthiness` クラスにて、以下のルールに従って判定を行います。
    - **False と判定されるケース**:
        - `null`
        - `Boolean`: `false`
        - `String`: 空文字、空白のみの文字、またはケース無視で `"false"`, `"no"`, `"off"` のいずれか。
        - `Number`: `0` または `0.0`。
        - `List` / `Map`: 要素が空の場合。
    - **True と判定されるケース**:
        - 上記以外のすべての値（非空の文字列、非ゼロの数値、要素を持つリスト/マップ等）。

## 16. 致命的なエラーによる停止 (`any_errors_fatal`)

特定のホストでエラーが発生した際、プレイ全体の実行を即座に停止するかどうかを制御します。現在、`graal-ansible` ではこの機能が完全に実装されています。

- **仕様**:
    - `any_errors_fatal` が `true` に設定されている場合、いずれか一箇所のホストでタスクが失敗（failed）または到達不能（unreachable）になると、そのプレイ内の後続のすべてのタスクの実行を、すべてのホストに対して停止します。
    - **判定タイミング**: 各タスクの実行完了直後、または `TaskQueueManager` が次のタスクの実行に移る前に行います。
    - **スコープ**: `Play` レベルまたは `Task` レベルで指定可能です。
- **実行エンジンでの実装**:
    - `TaskQueueManager` にて、エラー発生時に `any_errors_fatal` 設定をチェックし、有効な場合は内部の `playFatalError` フラグをセットします。
    - 以降のタスクやロールの実行ループにおいて、このフラグがセットされている場合は実行をスキップします。
    - **Linear 戦略との兼ね合い**: Ansible の標準的な挙動に合わせ、現在のタスクが全ターゲットホストで完了するのを待ってから（そのタスク内での他ホストの実行は継続）、次のタスク以降の実行を中止します。
- **データ構造**:
    - `Play` レコードおよび `Task` レコードに `Boolean anyErrorsFatal` フィールド（YAML では `any_errors_fatal`）を保持します。

## 17. 非同期タスク (Async Tasks: `async`, `poll`)

タスクをバックグラウンドで実行し、完了を待機または後で確認する仕組みです。本機能は `graal-ansible` において完全に実装されています。

### 17.1 基本的な実行フロー

- **非同期のトリガー**:
    - `async` キーワード（秒数）が指定されているタスクは、非同期実行の対象となります。
- **ジョブ ID (jid) の生成**:
    - 実行開始時に一意のジョブ ID (UUID) を生成します。
    - タスクの初期結果として `ansible_job_id` (jid) を返却します。
- **バックグラウンド実行**:
    - `TaskExecutor` は、タスクを専用の `ExecutorService` (スレッドプール) に投入して非同期に実行します。
    - 実行中、スレッドは `async` で指定されたタイムアウト時間を監視し、超過した場合はジョブを強制終了します。

### 17.2 ジョブ管理と永続化 (AsyncJobManager)

非同期ジョブの状態管理と永続化を行う `AsyncJobManager` が実装されています。

- **永続化ディレクトリ**:
    - Ansible 本家との互換性を保つため、ジョブの結果は管理ノードの `~/.ansible_async/` ディレクトリに保存されます。
    - 各ジョブの結果は、ジョブ ID をファイル名とした JSON ファイルとして保持されます。
- **結果ファイルのフォーマット**:
    - JSON 形式で保存され、開始時刻、終了フラグ、ジョブ ID、結果（`result`）等のフィールドを含みます。
- **メモリ管理**:
    - 実行中のジョブについては、`AsyncJobManager` がメモリ上でもステータスを保持し、高速な問い合わせに対応します。

### 17.3 ポーリング (`poll`) の制御

- **poll > 0 (待機型)**:
    - `TaskExecutor` は、ジョブを非同期で開始した後、指定された秒数間隔で `AsyncJobManager` を介して結果ファイルを確認します。
    - タスクが完了するか、`async` タイムアウトに達するまで呼び出し元をブロックします。
- **poll = 0 (投げっぱなし型)**:
    - ジョブを開始した直後に、`ansible_job_id` を含む初期結果を返して次のタスクへ進みます。
    - ユーザーは後続のタスクで `async_status` モジュールを使用して状態を確認する必要があります。

### 17.4 async_status モジュールとの連携

- **ステータス確認**:
    - `async_status` モジュールが実行されると、渡された `jid` に基づいて `AsyncJobManager` が `~/.ansible_async/<jid>` ファイルを読み取ります。
- **戻り値**:
    - ジョブが実行中の場合は `finished: 0` を、完了している場合は `finished: 1` と共にモジュールの実行結果を返却します。

### 17.5 スレッドプールとリソース管理

- **スレッドプール構成**:
    - 非同期タスク専用の `CachedThreadPool` を使用し、多数の同時非同期タスクに対応しています。
- **クリーンアップ**:
    - `TaskExecutor` のクリーンアップ処理（`close()`）において、スレッドプールの適切なシャットダウンが行われます。

### 17.6 データ構造

- `Task` レコードには以下のフィールドが保持されています：
    - `Integer asyncVal`: 非同期実行のタイムアウト（秒）。YAML の `async` に対応。
    - `Integer poll`: ポーリング間隔（秒）。

## 18. 並列実行制限 (`throttle`)

特定のタスク、ブロック、またはプレイにおいて、同時に実行できるホスト数を制限します。

- **実装方針**:
    - `throttle` キーワードで指定された数値を評価します。テンプレートもサポートされており、実行時に動的に評価されます。
    - `FreeStrategy` において、タスクごとに `Semaphore` を使用して、同時に実行されるホストの数を制限します。
    - `throttle` が `Play` レベルで指定されている場合、そのプレイ内のすべてのタスクにデフォルト値として適用されます。
    - `Task` または `Block` レベルで指定されている場合は、そちらが優先されます。
- **データ構造**:
    - `Play` および `Task` レコードに `Object throttle` フィールドを保持します。
