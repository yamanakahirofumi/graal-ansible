# Ansible Vault 復号サポート仕様 (Ansible Vault Decryption Support)

`graal-ansible` において、暗号化された変数やファイルを安全に扱うための、ネイティブ Java による Ansible Vault 復号機能の設計仕様および新機能の提案（[提案]）について定義します。

## 1. 背景と目的 (Background & Objectives)

Ansible Vault は、Playbook や変数ファイル内のパスワード、秘密鍵などの機密情報を暗号化して安全に Git 管理等に含めるための標準機能です。
現行の `graal-ansible` では、`!vault` などのカスタムタグを `YamlParser` でエラーを出さずに透過的にフォールバック（文字列として保持）するのみに留まっており、実際のデータの復号はサポートされていません。

本提案では、外部の Python プロセスや GraalPy 上の重量ライブラリ（`cryptography` 等）に依存することなく、**Java 標準の暗号ライブラリ (Java Cryptography Architecture / JCA) を利用して、制御ノード上で高速かつスレッドセーフに復号処理を行う**ネイティブなメカニズムを提供することを目的とします。

## 2. 復号のアルゴリズム仕様 (Decryption Algorithm Specification)

Ansible Vault 1.1 形式（主に `AES256`）の復号を行います。

### 2.1 データフォーマット (Vault Text Format)

Vault で暗号化されたテキストデータは、必ず以下の形式のヘッダーから始まります。

```text
$ANSIBLE_VAULT;1.1;AES256
```

このヘッダー以降のペイロードは、16進エンコードされた文字列が複数行（通常 80 文字幅）に分割されて表現されます。この16進文字列をデコードすると、以下の3つのブロックが改行文字（`\n`）区切りで格納されています。

1. **ソルト (Salt)**: 鍵導出に用いる32バイト（Hex表記で64文字）のソルト。
2. **HMAC署名**: データの改ざん検知に用いる32バイト（Hex表記で64文字）の署名。
3. **暗号ペイロード (Cipher Text)**: 実際の暗号化データ。

### 2.2 鍵導出プロセス (Key Derivation - KDF)

パスワード文字列と取得したソルトから、暗号キー、HMAC検証用キー、および初期化ベクトル（IV）を導出します。

| パラメータ | 設定値 | 補足 |
| :--- | :--- | :--- |
| **KDF アルゴリズム** | `PBKDF2WithHmacSHA256` | Java 標準の `SecretKeyFactory` を使用 |
| **反復回数 (Iterations)** | `10000` | Ansible 1.1 仕様の既定値 |
| **出力鍵長** | `80` バイト（640 ビット） | 各キー分割用の総バイト長 |

導出された 80 バイトは以下の通り分割して使用します。

- **AES 復号キー**: 先頭の 32 バイト (0〜31 バイト)
- **HMAC 検証キー**: 次の 32 バイト (32〜63 バイト)
- **初期化ベクトル (IV)**: 残りの 16 バイト (64〜79 バイト)

### 2.3 整合性検証 (Integrity Verification)

データの改ざんや、パスワードの誤りを検知するため、復号を行う前に必ず HMAC 署名の整合性を検証します。

1. **HMAC 鍵** を使用し、**暗号ペイロード** に対する **HmacSHA256** 値を算出します。
2. 算出した値と、データ内の「HMAC署名」を比較します。
3. 一致しない場合は、`RuntimeException`（「Decryption failed or invalid password」等）をスローし、該当するタスクまたはプレイの実行を失敗（failed）として処理します。

### 2.4 暗号復号 (Decryption)

整合性検証が正常に完了したのち、**AES復号キー** と **IV** を用いてデータを復号します。

- **暗号化方式**: `AES/CTR/NoPadding` (AES256-CTR)
- **デコード後の処理**: 復号されたバイト配列を、必要に応じて UTF-8 文字列に変換して返却します。

## 3. 処理フローと設計 (Architecture & Flow)

本機能は、管理ノード（制御ノード）上において、YAML 解析および変数解決のフェーズで透過的に実行されます。

```text
[Playbook YAML] -> (YamlParser)
                      |  !vault タグ検知
                      v
                [VaultTagConstructor] -> (VaultDecryptor) -> [プレーンテキスト/オブジェクト]
                      |                                       |
                      +------- パスワードファイルの解決 --------+
```

### 3.1 統合ポイント (Integration Points)

1. **`YamlParser.java` との統合**:
   - SnakeYAML の `Constructor` をカスタマイズし、`!vault` タグを持つカスタムノード（Scalar）を検出した際に `VaultDecryptor` を呼び出して即時復号、あるいは遅延評価可能な `VaultValue` オブジェクトとしてマッピングします。
2. **`VariableResolver.java` との統合**:
   - インラインで定義された Vault 変数が含まれる場合、テンプレートの展開（Jinja2 レンダリング）の直前に自動的に復号処理が走るようにします。

## 4. CLI オプションの拡張 (CLI Options)

パスワードをエンジンに渡すため、以下のオプションを `PlaybookCli` に追加提案します。

| オプション | 短縮形 | 説明 |
| :--- | :--- | :--- |
| `--vault-password-file` | - | 復号用パスワードがプレーンテキストで記載されたファイルのパスを指定します。 |
| `--ask-vault-pass` | `-J` | 実行時にコンソールからインタラクティブにパスワードを入力させます。 |

## 5. セキュリティ設計 (Security Considerations)

1. **メモリ上の保護**:
   - パスワードや復号された文字列は、可能な限り `String`（イミュータブルでガベージコレクションまでメモリに残留する）の使用を避け、`char[]` もしくは `byte[]` として処理し、使用後は直ちに `0` やヌル文字で上書き（Wipe）できる設計を推奨します。
2. **パスワードファイルの権限管理**:
   - `--vault-password-file` で指定されたファイルのアクセス権限（パーミッション）が適切に保護されているか、エンジン起動時にチェックを行う機構を導入予定とします。
